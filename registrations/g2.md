# G2: the development-mode twin

*Registered 2026-11-21 · GPU runs · result 2026-11-22*

| | |
|---|---|
| **Question** | Does vLLM's development mode (`VLLM_SERVER_DEV_MODE`) move the saturated cache-off throughput, and so the cold floor and the margins? |
| **Runs** | 4 runs (of the shared registration's 16): T4's 2048 cache-off config at λ = 3 and 4, once with `server.env.VLLM_SERVER_DEV_MODE: "1"` and once without, in the order off 3, on 3, on 4, off 4, on the same day. Configs `configs/sweep_g2_l1pl350cl_pc_off_b2048_{dev,nodev}.yaml`. Each run's mode is read from the server's route log (`g2.check_mode`). |
| **Outcome rule** | `g2.outcome`: r = throughput_on / throughput_off − 1 per rate. In order: `dev_undefined` (a pair missing, or a counted run keeps up: throughput ≥ 0.95 × planned) → `dev_neutral` (\|r\| ≤ 0.02 at both rates) → `dev_moves` (\|r\| > 0.02 at both, same sign) → `dev_unclear`. |
| **Prediction** | `dev_neutral` 0.82, `dev_unclear` 0.10, `dev_moves` 0.04, `dev_undefined` 0.04 (the reviewing panel's: within ±2 %, P 0.9). |
| **Decision under each outcome** | `dev_neutral`: the development-mode caveat is deleted for the cold floor and the margins and replaced by the measured r; the warm side keeps one sentence (G2 did not test cache-on). `dev_moves`: every margin is recomputed against a floor corrected by r. `dev_unclear`, `dev_undefined`: the caveat stays and r is printed. |
| **Adversarial review** | One round, shared by G1 and G2, before registration: four blocking and ten advisory items, all handled; two not applied as proposed (G-9: the caveat's deletion narrowed to the floor side instead of adding a cache-on pair; G-10b: the mode-off twins not moved, so that G2's pairs are not split). No second round. |
| **Result** | `dev_neutral`: throughput with the mode on against off 1.7955 against 1.7970 req/s at λ = 3 (r = −0.0008) and 1.8530 against 1.8409 at λ = 4 (r = +0.0066); all four runs were behind (none keeps up). |
| **Prediction held** | yes (likeliest outcome: `dev_neutral` at 0.82) |
| **Not separated** | A mode effect under ≈ 1 % is not separable from run-to-run change (one pair per rate); the effect on warm (cache-on) capacity is not measured; the mode check reads a route log line, so a server that logs it without the mode in effect is not ruled out. |
| **In the paper** | Appendix A, 'the development-mode twin'; §6 (P64; also P52). |
| **Notes** | One registration with G1. Readout: against T4's same-rate runs of the same config about 10 h earlier, the mode-on runs are +1.1 % and +0.4 %, so the mode's effect is no larger than the change of one config across a day. |

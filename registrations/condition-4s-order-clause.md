| **Question** | Do the traces of stuck runs made after this registration follow the plan's literal order from the trigger (hit rate drops; recomputed prefill rises; running batch N grows; KV fills and cached prefixes are evicted sooner; hit rate stays low), with preemptions low throughout? |
| **Runs** | 0 GPU h. It judges valid runs whose `load.verdict` is `stuck` and whose run id is later than `20261114-102959`: REG-24's burst run (L1, λ = 2.0, seed 43), D1's capped burst runs (a cell of their own) and one cache-wipe run at L1, λ = 2.0 (REG-25, seed 44). |
| **Outcome rule** | `order.judge` and `order.table`: each onset is the first point of a 10 s grid from the origin at which a trailing 60 s window meets its level (reuse ≤ baseline − `stuck_hit_drop`; session uncached rate ≥ 2 × baseline; N ≥ 2 × baseline; KV ≥ 0.80). The order fails when a signal the plan puts later crosses more than 70 s before one it puts earlier; also judged are evicted sooner, stays low (reuse) and stays high (mean N ≥ 2 × baseline, mean KV ≥ 0.80) over the end window, and preemptions at most 0.01 per request that ended ok. Labels: `follows`; `does_not_follow` (with `failed`, and `u_only` True when every failure is u crossing late); `undefined`; from `table` also `invalid` and `not_judged (<verdict>)`. A cell meets the clause when more than half of its judged runs read `follows` (k > n/2). |

| **Decision under each outcome** | Burst `does_not_follow`: C1 at λ = 2.0 cannot cite the order clause from burst runs; burst `follows`: the run meets the clause and the earlier 0-of-16 pattern is reopened.
